# Embedo.ai — Master Knowledge & Engineering Architecture Guide

> **Note for AI Coding Assistants (Claude Code, Cursor, Copilot, Antigravity)**:
> This document is the source of truth for the Embedo.ai hardware architecture copilot platform. All requirements, pipeline designs, API endpoints, rate limit quotas, UI interaction contracts, and database models are codified here.

---

## 🚀 1. Product Overview & Core Vision

Embedo.ai is an AI-native embedded hardware systems design platform. It translates natural language hardware specifications into production-grade electronic system architectures:
- **Functional Block Diagrams** (Microcontrollers, Sensors, Actuators, Communication Buses)
- **Power Trees** (Voltage Domains, Regulators, Battery Management, Quiescent Current Budgets)
- **Protocol / Interface Maps** (I2C, SPI, UART, CAN, USB, BLE, Wi-Fi pin & bus wiring)
- **Interactive Bill of Materials (BOM)** (Grounded with real manufacturer part numbers and datasheet links)
- **Version Control & Iterative Refinement** (`v1.0`, `v1.1`, `v1.2` with full snapshot history and rollback)

## 🧩 2. User Interaction & Chat UI Contract

Based on the UI designs and Copilot Chat requirements:

### A. Copilot Chat Panel (Left Sidebar)
1. **Header & Mascot Expressions (5 Core States)**:
   - `IDLE`: Calm and ready.
   - `THINKING`: Analyzing and reasoning (triggered on `ai_call_started`).
   - `PROCESSING`: Working on it (triggered during `stage_update` / pipeline execution).
   - `SUCCESS`: Completed successfully (triggered on `done`).
   - `ALERT`: Attention needed / clarification required (triggered on `clarification_needed` or `error`).
2. **Assistant Message Structure**:
   - **Status Badge**: `Architecture generated successfully!`
   - **Design Summary**:
     - `MCU`: Selected microcontroller (e.g. ESP32-S3, nRF52840, STM32)
     - `Power`: Power supply stage & regulation (e.g. 5V in, 3.3V LDO, LiPo charger)
     - `Interfaces`: Active protocols (e.g. RFID, BLE, Tamper input, SSR Outputs)
     - `Security`: Hardware security features (e.g. Secure boot, flash encryption, tamper detect)
   - **Action Buttons**: Copy to clipboard, Thumbs Up (like), Thumbs Down (dislike) $\rightarrow$ connects to `POST /api/v1/sessions/:id/feedback`.
3. **Refine Further Suggestion Chips**:
   - Dynamic chips generated by the AI based on the current architecture:
     - `[Add battery backup]`, `[Add Wi-Fi connectivity]`, `[Optimize for low power]`, `[Add audit logging]`, `[Change to PoE]`, `[Add enclosure sensor]`
4. **Applied Changes / Version Control Block**:
   - Lists version snapshots with timestamp relative format:
     - `v1.2` Replaced relay outputs with SSRs / Added tamper detection input (Just now)
     - `v1.1` Added buzzer and status LEDs / Refined power supply stage (2m ago)
     - `v1.0` Initial architecture generated (5m ago)
   - `View all versions` link $\rightarrow$ opens version history modal / rollback.
5. **Selected Engineering Assumptions**:
   - Editable technical constraints drawer: Input Voltage, Relay type, Tamper Detection, Wireless modes, Operating Temperature.

## 🛡️ 3. Sufficiency Gate & Anti-Spam Protection

To prevent wasting costly LLM tokens on non-sensical inputs (e.g. `"asdasdasdasdasd"`, `"qwerty"`, keyboard mashing):
1. **Upfront Heuristic Check (`isGibberishOrSpam`)**:
   - Rejects repeated n-grams (`asdasd`, `abcdabcd`).
   - Rejects repetitive character strings (`aaaaaa`, `111111`).
   - Rejects strings with unnatural vowel/consonant ratios.
2. **Immediate Session Creation Handling (`POST /api/v1/sessions`)**:
   - If the initial intent is detected as ambiguous/gibberish, the session is **immediately created with `status: "CLARIFICATION_REQUIRED"`** (instead of `PENDING`), with the assistant clarification message pre-populated in the chat history.
   - This saves background Redis/BullMQ processing and returns an instant accurate state to the client.
3. **Sufficiency Gate in Worker Pipeline (`checkSufficiency`)**:
   - Checks if `deviceType`, `purpose`, or functional `subsystems` are defined.
   - If insufficient or gibberish $\rightarrow$ immediately stops pipeline and prompts user with clarification questions:
     > *"The hardware description provided is unclear or incomplete. Please describe an embedded product or concept (e.g. 'Battery-powered BLE asset tracker with GPS and accelerometer')."*

### 4. Governance / Moderation Tiers (`moderation.service.ts`)

Every text entry point (`POST /sessions`, `POST /sessions/:id/discuss`) is screened **after**
validation (so only bounded text reaches a provider) and **before** any generation model is called:

1. **Tier 1 — deterministic wordlist** (`banned-terms.ts`): free, sub-millisecond. Gibberish is
   screened at Tier 1 only, so keyboard mashing never incurs provider spend.
2. **Tier 2 — provider moderation API**: hate / harassment / sexual / self-harm / violence.
3. **Tier 3 — domain classifier (Case M via the model router)**: hardware-specific misuse
   (weapons, covert surveillance, jamming, skimmers, access bypass). Legitimate engineering terms
   — "kill switch", "tamper detection", "lock controller" — are explicitly *not* violations.

If Tier 2/3 errors, behaviour follows `MODERATION_FAIL_MODE`: **`closed` in production** (request
refused with `503`), `open` elsewhere. Violations are written to `moderation_events` and counted
toward the rolling strike window.

## ⏱️ 4. User Quotas & Rate Limits (Phase 1 MVP)

Enforced in `rate-limit.middleware.ts` (Redis token buckets, with an in-memory insurance limiter
if Redis is unreachable) and `sessions.service.ts`:

- **Guest / Anonymous Users** (`anonSessionToken`, server-issued 64-char hex):
  - **Max 6 chat messages / refinement turns** per session → `403 GUEST_QUOTA_EXCEEDED`.
  - **Session creation: 5/hour keyed by IP** (never by the client-supplied token, which would be
    trivially rotated to mint fresh quota).
- **Free Registered Users** (`userId`):
  - **Max 20 messages** per project session → `403 SESSION_QUOTA_EXCEEDED`.
  - **Max 3 architectures in flight** (`PENDING`/`PROCESSING`/`CLARIFICATION_REQUIRED`); finished
    and failed projects do not occupy a slot.
  - Session creation: 20/hour per account.
- **Absolute cost ceiling:** `SESSION_CREATE_DAILY_MAX_PER_IP` (default 50/day) applies to everyone.
- **Other limiters:** global 100/min per IP, auth 10/min per IP, password reset 3/hour per IP,
  discuss 30/hour per session.
- **Moderation Strikes**:
  - `MODERATION_STRIKE_LIMIT` (default 3) within `MODERATION_STRIKE_WINDOW_SECONDS` (default 1h)
    → suspension for `MODERATION_SUSPENSION_SECONDS` (default 24h), stored in Redis with a TTL.
  - Applies to **anonymous actors as well as registered users**. `users.moderationStrikes` is a
    lifetime audit counter; it is not the suspension trigger. Permanent bans remain a manual
    `users.suspendedAt` action.

## 💬 4a. Conversation Routing (`conversation-router.service.ts`)

Generation is expensive, so it only runs when the engineer actually asks for it. Every inbound
message (session creation **and** `/discuss`) is classified by **Case F** into:

- **`generate`** — a hardware brief, or an explicit ask to design/generate/build an architecture,
  diagram or BOM → the pipeline is queued. The sufficiency gate still asks for missing details
  first, so nothing is guessed.
- **`discuss`** — a question, explanation request, or hardware talk with no ask to build → Luna
  (Case E) answers concretely and closes by offering to generate. **No pipeline run.**
- **`off_topic`** — not embedded hardware → the fixed off-topic reply, no further model calls.

The same call returns the **project title**. Titles are never derived from raw user text: doing so
put profanity straight into the project name and sidebar. It is stored in `design_sessions.title`
and served as `projectTitle`; when there is no title (off-topic, or a request blocked by
moderation before any model call) the UI shows `New project`.

Off-topic detection is **model-based on purpose**. An earlier keyword screen rejected real
hardware whenever a chit-chat word appeared in it ("solar powered weather station", "ESP32 YouTube
subscriber counter", "reflow recipe for lead-free solder"), so it was removed. `isGibberishOrSpam`
(`sufficiency-gate.ts`) still screens keyboard mashing at zero cost — "asdasd" cannot be mistaken
for hardware — and Case B repeats the off-topic judgement during intent parsing as a second line of
defence before synthesis.

## 🔄 4b. Session State Machine

`PENDING → PROCESSING → DONE` with two branches: `CLARIFICATION_REQUIRED` (sufficiency gate or
gibberish) and `FAILED` (retryable via `POST /sessions/:id/retry`). `SYSTEM` is an internal,
non-API-readable session used to attribute background AI spend (e.g. datasheet ingestion) to the
`ai_calls` ledger. The set is enforced by the `design_sessions_status_check` database constraint —
adding a status requires a migration.

## ⚡ 5. Real-Time Streaming & Socket.IO Events

- **Namespace**: `/ws/sessions`
- **Room**: `session:<sessionId>`
- **Handshake is authenticated and authorized**: the connection must present a valid access token
  (matching `session.userId`) or the session's `anonSessionToken`. Sessions with no owner are
  refused. Events are delivered once: the API emits directly (fanned out across cluster workers by
  the Socket.IO Redis adapter), while the BullMQ worker publishes to Redis and the API forwards.
- **Live Progress Checklist States (Electron Ali Design Spec)**:
  - Each step in the assistant execution card transitions dynamically:
    - `✓ Completed` (Green checkmark)
    - `⟳ In Progress / Resolving` (Pulsing teal spinner)
    - `· Upcoming / Pending` (Muted bullet dot)
    - `⚠ Warning / ✕ Failed` (Alert badge)
  - **Standard Embedded Pipeline Steps**:
    1. `✓ Reading intent` (Intent extraction & constraint parsing)
    2. `⟳ Resolving modules` (Component catalog RAG & part selection)
    3. `· Checking library coverage` (Datasheet grounding & package footprints)
    4. `· Assigning pins` (Electrical domains, GPIO & bus routing)
    5. `· Rendering` (Diagram layout projection & BOM generation)
- **Background Execution Banner**:
  - *"Planning a project before starting to build..."*
  - *"Embedo is synthesizing your architecture in the background. Once complete, you'll see it rendered here."*
- **Events Emitted by Backend**:
  1. `stage_update`: `{ step: 1..7, label: string, progress: 0..100 }`
  2. `pipeline_step`: `{ stepId: string, label: string, detail?: string, status: 'running' | 'completed' | 'warning' | 'failed', icon?: string }`
  3. `ai_call_started`: `{ taskCase: 'A' | 'B' | 'C' | 'D' }` $\rightarrow$ Mascot moves to `THINKING`.
  4. `ai_call_completed`: `{ taskCase: string, schemaPass: boolean, latencyMs: number }`
  5. `clarification_needed`: `{ questions: string[] }` $\rightarrow$ Mascot moves to `ALERT`.
  6. `done`: `{ architecture: ProjectedArchitecture }` $\rightarrow$ Mascot moves to `SUCCESS`.
  7. `error`: `{ message: string, retryable: boolean }` $\rightarrow$ Mascot moves to `ALERT`.

## 🤖 6. AI Model Routing & Tiers

- **Sol Tier (`gpt-4o`)**:
  - `TaskCase A`: Core hardware synthesis & canonical design graph generation (`buildCanonicalDesignGraph`).
  - `TaskCase D`: Complex power domain calculations & pinout constraint solving.
- **Luna Tier (`gpt-4o-mini`)**:
  - `TaskCase B`: Hardware intent parsing (`parseHardwareIntent`), Discuss-First chat copilot (`discuss`).
  - `TaskCase C`: Topology validation, auto-repair, electrical rules checking.
  - `TaskCase E`: Conversational copilot replies (`generateCopilotReply`) — answers questions and
    offers to generate, without running the pipeline.
  - `TaskCase F`: Conversation routing + project title (`routeMessage`, see §4a).
  - `TaskCase M`: Moderation domain classification (Tier 3).
- **Embeddings**: `text-embedding-3-small` (1536 dims) for component catalog vector cosine similarity.

## 🚢 8. Deployment Commands (espark-kuwait pattern)

- **Local Development**:
  ```bash
  docker-compose up -d    # Starts Postgres (pgvector) + Redis
  npm run dev             # Starts Express + Socket.IO on port 4000
  npm run worker          # Starts BullMQ worker
  npm run db:studio       # Web GUI to inspect DB records
  ```
- **Automated Production VPS Deployment**:
  ```bash
  VPS_PASSWORD='your_password' ./deploy.sh backend
  ```
- **Strict Guidelines** (now machine-enforced by `npm run verify` / CI):
  - Never run git commits/pushes from automated agents.
  - Maintain 100% strict TypeScript — `@typescript-eslint/no-explicit-any` is an **error**.
  - Vendor AI SDKs (`openai`, `@anthropic-ai/sdk`, `@google/generative-ai`) may only be imported
    inside `src/modules/ai/providers/**`; an ESLint `no-restricted-imports` rule enforces the
    boundary. Everything else goes through `aiRouterService` / `modelProviderService`.
  - Every AI call must be logged to `ai_calls` **before** its result is used. `aiRouterService`
    throws if the ledger write fails — cost and training data are never silently dropped.
  - `prisma db push` is for local prototyping only. Schema changes ship as migrations.
